# SKILL: rust-miniredis-dev

Конвенции и технические решения `miniredis-rs`. Загружать при работе над любым кодом проекта.

## Что за проект

In-memory KV-сервер на Rust, реализующий проволочный протокол Redis (RESP) поверх голого TCP,
с TTL и LRU-вытеснением за O(1). Учебный pet-проект: ценность — техника, не фичи. Самодостаточный
бинарь, без внешних зависимостей и Docker. План — `docs/PLAN.md` / `docs/TECHNICAL_PLAN.md`.

## Конкурентная модель — РЕШЕНИЕ

**thread-per-connection на `std::net`, БЕЗ `tokio` в v1.**

Обоснование: главная учебная ценность — потоковый разбор TCP и синхронизация разделяемого
состояния. Async-рантайм (`tokio`) абстрагирует буферизацию и фрагментацию под `AsyncRead` —
ровно то, что мы хотим прочувствовать руками. Поэтому:

- `std::net::TcpListener` слушает; на каждое соединение — `std::thread::spawn`.
- Хранилище общее: `Arc<Mutex<Store>>` (одна блокировка в v1; шардирование/`RwLock` — POST_MVP,
  только если `redis-benchmark` покажет мьютекс узким местом).
- `read()` голый — обработчик соединения ОБЯЗАН сам буферизовать и возобновлять парсинг на
  границе фрагмента (см. паттерн ниже).

Миграция на `tokio` — задокументированный POST_MVP-пункт, не MVP-зависимость. Не тащить
`tokio` в MVP.

## LRU — РЕШЕНИЕ

O(1) и на `get` (touch → голова), и на вытеснение (хвост = least-recently-used). Основной путь —
свой intrusive doubly-linked list; безопасная реализация на Rust — **slab/арена**: `Vec<Node>` +
индексы `usize` (и `Option<usize>`) вместо сырых указателей/ссылок, без `unsafe`. Запасной путь —
крейт `lru`; если берём — зафиксировать причину в `docs/TECHNICAL_PLAN.md` (Этап 4). По умолчанию
пишем сами — это и есть учебная цель Этапа 4. Линейный поиск самого старого ключа НЕ допускается.

## Паттерн тестирования протокольного парсинга — КЛЮЧЕВОЕ

RESP идёт по потоковому TCP: один `read()` возвращает половину кадра, ровно один кадр или
несколько кадров подряд. Наивный парсер проходит `redis-cli` (шлёт аккуратными пакетами) и
ломается на реальной фрагментации. Поэтому тесты кодека ОБЯЗАНЫ включать не только happy-path:

1. **Побайтовое скармливание.** Один кадр подаётся в `Parser::feed` по 1 байту; `try_parse()`
   возвращает `Incomplete` на каждом шаге, кроме последнего, где отдаёт полный `Value`.
   Частичные байты между вызовами НЕ теряются и НЕ потребляются повторно.
2. **Случайные чанки.** Тот же кадр бьётся на чанки произвольной, в т.ч. неровной, длины —
   результат парсинга идентичен цельному.
3. **Слипшиеся кадры.** Несколько кадров одним чанком → последовательные `try_parse()` отдают
   их по одному, ничего не теряя и не смешивая.
4. **Property-инвариант.** Для ЛЮБОГО разбиения байт кадра на чанки декодирование даёт один и
   тот же `Value`. Реализовать через генератор всех/случайных точек разбиения (хелпер вида
   `feed_fragmented(parser, bytes, chunk_sizes)`).
5. **Round-trip.** `decode(encode(v)) == v` для каждого варианта `Value` (Simple/Error/Integer/
   Bulk/Null/Array), включая вложенные массивы и бинарные (не-UTF8) bulk-строки.
6. **Ошибки протокола.** Битый префикс длины, неизвестный тип-байт, отрицательная длина
   (кроме легитимного `$-1` null) → `ParseError::Protocol`, без паники.

Это соответствует конвенции портфеля «тестам нужен интеграционный ярус»: юнит-тесты кодека +
детерминированный интеграционный фейк (реальный `Store` + реальный кодек, без сети) + e2e через
живой `redis-cli`/`redis-benchmark` по требованию. Мок-HTTP-стиль недостаточен — он не ловит
фрагментацию.

## Кодстайл и гигиена

- Комментарии/идентификаторы — английские; заглушки — `// TODO(Этап N): ...`, снимать по мере
  реализации.
- Перед коммитом: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`.
- Ключи/значения — `Vec<u8>` (RESP bulk бинарен, не обязан быть UTF-8); не приводить к `String`
  на пути хранения.
- Ошибки клиенту — RESP-error (`-ERR ...`), не паника обработчика; паника рвёт только свой поток,
  но всё равно недопустима как способ обработки кривого ввода.
