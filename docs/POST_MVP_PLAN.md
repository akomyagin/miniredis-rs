# miniredis-rs — POST_MVP_PLAN

Всё ниже **вырезано из MVP полностью** и рассматривается только после того, как MVP (Этапы
0–5: RESP-кодек, GET/SET/DEL/EXPIRE, TTL+sweeper, O(1) LRU, нагрузочный тест) закрыт и
стабилен. Порядок — примерная приоритизация по соотношению «учебная ценность / сложность»,
не обязательство.

## 1. Pub/Sub

`SUBSCRIBE` / `UNSUBSCRIBE` / `PUBLISH`. Учебная тема — рассылка сообщений подписчикам по их
соединениям (fan-out), управление списками подписок и жизненным циклом каналов. Затрагивает
конкурентную модель: обработчик соединения должен уметь получать пуши, не инициированные
клиентским запросом, — вероятный триггер для пересмотра thread-per-connection.

## 2. Транзакции MULTI/EXEC

`MULTI` / `EXEC` / `DISCARD` / `WATCH`. Учебная тема — буферизация команд на соединении и
атомарное применение; `WATCH` вводит оптимистичную блокировку (CAS по версии ключа). Заставляет
аккуратно продумать границы блокировки разделяемого хранилища.

## 3. Персистентность

- **RDB-подобные снапшоты:** периодический дамп всего хранилища в файл; загрузка при старте.
  Тема — сериализация в памяти и атомарная запись (write-to-temp + rename).
- **AOF (append-only file):** журналирование каждой мутирующей команды; воспроизведение при
  старте; компакция журнала. Тема — durability, ordering, восстановление после сбоя.

## 4. Репликация

Master → replica: асинхронная доставка потока команд одному или нескольким репликам,
first-sync снапшотом + последующий стрим. Тема — консистентность распределённого состояния,
поверх которой естественно ложится AOF из пункта 3.

## 5. Больше типов данных

За рамками простого string-KV: списки (`LPUSH`/`RPUSH`/`LRANGE`), хеши (`HSET`/`HGET`),
множества, sorted sets. Каждый — отдельная структура данных со своими O-характеристиками.

## 6. Async-миграция протокольного слоя (`tokio`)

Только если реальный профиль потребует **тысяч одновременных idle-соединений**, где
thread-per-connection упирается в память/переключение контекста. Мигрировать `src/resp.rs` под
`AsyncRead`/`AsyncWrite`. Явно вынесено сюда, потому что MVP намеренно сделан на `std::net`
ради обучения (см. TECHNICAL_PLAN.md, Этап 5) — async не является MVP-зависимостью.

## 7. Оптимизация синхронизации хранилища

Если Этап 5 покажет, что глобальный `Mutex<Store>` — узкое место под `redis-benchmark`:
шардирование пространства ключей по нескольким мьютексам или переход на `RwLock` для
read-heavy нагрузки. Оптимизация, а не корректность, — поэтому после MVP.
