# miniredis-rs — TECHNICAL_PLAN

Детальный технический план: стек, ключевые решения, разбивка по Этапам.

## Стек и ключевые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Язык / edition | Rust 2021, toolchain ≥ 1.96 | второй Rust-проект в портфеле; edition 2021 — самый обкатанный |
| Асинхронность | **Нет `tokio` в v1** — только `std::net` | цель проекта — вручную прочувствовать потоковый TCP и синхронизацию разделяемого состояния; async-рантайм спрятал бы ровно эту механику за своими абстракциями |
| Конкурентная модель | **thread-per-connection** (`std::thread::spawn` на соединение) | простейшая корректная модель для учебного KV; операционные системы тянут сотни-тысячи потоков, а профиль нагрузки pet-проекта — десятки соединений. Переход на async — задокументированный POST_MVP-пункт, не MVP-зависимость |
| Разделяемое хранилище | `Arc<Mutex<Store>>` в v1 | одна блокировка проще и корректнее; шардирование/`RwLock` — оптимизация, к которой возвращаемся только если `redis-benchmark` покажет, что мьютекс — узкое место (см. Этап 5) |
| LRU за O(1) | intrusive doubly-linked list, вручную | см. Этап 4 — решение и trade-off ниже |
| Версия протокола | RESP2 | достаточно для GET/SET/DEL/EXPIRE и совместимо с `redis-cli`; RESP3 — за скоупом |
| Внешние зависимости MVP | нулевые (или один `lru`, если пересмотрим Этап 4) | самодостаточный бинарь, никакого Docker Compose, тест голым `redis-cli` |

### Почему `std::net`, а не `tokio` (зафиксировано)

Главная учебная ценность — потоковый парсинг и синхронизация. `tokio` дал бы `AsyncRead`,
который сам буферизует и абстрагирует фрагментацию, — то есть спрятал бы главную мину проекта.
Thread-per-connection оставляет `read()` голым: обработчик обязан сам буферизовать и
возобновлять парсинг на границе фрагмента. Это дороже по памяти на соединение, но именно то,
что мы хотим прочувствовать. Если понадобится масштаб на 10k+ соединений — миграция
`src/resp.rs` на `tokio` вынесена в POST_MVP.

## Разбивка по Этапам

Каждый Этап — отдельная ветка от `master` → PR → merge (см. `CLAUDE.md`).

### Этап 0 — Скелет (готов)

- `cargo init`, `Cargo.toml` с нулевыми рантайм-зависимостями и зафиксированным решением по
  конкурентности в комментарии.
- Модули-заглушки: `src/resp.rs` (типы `Value`/`ParseError`/`Parser` + `encode`, все с
  `TODO(Этап N)`), `src/store.rs` (`Entry`/`Store` с `TODO(Этап N)`).
- `src/main.rs` биндит TCP и принимает соединения (accept-and-drop).
- **Критерий готовности:** `cargo check` и `cargo build` проходят чисто.

### Этап 1 — RESP-кодек (протокольный слой)

Сердце проекта. RESP2-типы: `+` simple, `-` error, `:` integer, `$` bulk, `*` array; терминатор
кадра — CRLF. Клиентская команда приходит как `*`-массив bulk-строк.

- **Декодер `Parser`** — буферизующий и **возобновляемый**:
  - `feed(&[u8])` — дописать пришедшие из сокета байты во внутренний буфер.
  - `try_parse() -> Result<Value, ParseError>` — либо один полный кадр, либо
    `Err(ParseError::Incomplete)` без потребления частичных байт; потреблённые байты
    вычёркиваются из буфера, чтобы следующий вызов возобновился ровно с границы кадра.
  - Явный `ParseError::Protocol` на битом префиксе длины / неизвестном типе-байте.
- **Энкодер `encode(&Value) -> Vec<u8>`** — зеркало декодера для пути ответа.
- **Тестирование (обязательно, см. SKILL.md):** помимо happy-path — тесты с **искусственно
  фрагментированными** чтениями: скармливать один и тот же кадр по 1 байту за раз, случайными
  чанками, несколько кадров одним чанком. Property-подход: для любого разбиения байтов кадра
  на чанки результат парсинга идентичен.
- **Критерий:** round-trip `encode ∘ decode` для всех типов; фрагментация любой гранулярности
  не ломает парсер.

### Этап 2 — Базовые команды над `HashMap`+`Mutex`

- `Store` = `HashMap<Vec<u8>, Entry>` за `Mutex`, обёрнут в `Arc` для шаринга между потоками.
- `main` принимает соединение → `thread::spawn` → цикл: `read()` в буфер → `parser.try_parse()`
  → диспатч → `encode` ответа → `write()`.
- Команды: `PING` (→ `+PONG`), `SET key val`, `GET key` (→ bulk или `$-1` null), `DEL key...`
  (→ integer числа удалённых). Регистр команды нечувствителен.
- Некорректные аргументы → RESP-error (`-ERR wrong number of arguments ...`).
- **Критерий:** `redis-cli -p 6379 set foo bar` / `get foo` / `del foo` работают вживую.

### Этап 3 — TTL

- `Entry.expires_at: Option<Instant>`.
- `SET key val EX <sec>` / `PX <ms>`; отдельная `EXPIRE key <sec>`; `TTL key` для проверки.
- **Ленивая экспирация:** `get`/`del` трактуют просроченный ключ как отсутствующий и удаляют
  его на месте.
- **Фоновый sweeper:** отдельный поток периодически (напр. раз в 100 мс) зовёт
  `store.sweep_expired()`, чтобы память не текла из-за ключей, к которым больше не обращаются.
- **Критерий:** ключ с `EX 1` исчезает через секунду и по `get`, и (без обращения) усилиями
  sweeper'а.

### Этап 4 — LRU-вытеснение O(1)

**Решение и trade-off (зафиксировать при реализации):**

- **Основной путь — свой intrusive doubly-linked list**, вплетённый в записи `HashMap`: `get`
  переносит узел в голову списка (touch) за O(1), при переполнении ёмкости вытесняется хвост
  (least-recently-used) за O(1). Это и есть учебная ценность Этапа — руками сделать структуру
  данных с O(1) и на доступ, и на вытеснение, а не линейный поиск самого старого ключа.
- **Rust-нюанс:** «настоящий» intrusive list с сырыми указателями требует `unsafe`. Допустимая
  безопасная альтернатива — slab/арена (`Vec<Node>` + индексы-«указатели» `usize`,
  `Option<usize>` вместо ссылок), которая даёт ту же O(1)-семантику без `unsafe`. **Выбор
  slab-арены задокументировать в этом файле при реализации.**
- **Запасной путь:** крейт [`lru`](https://crates.io/crates/lru). Если берём его — **явно
  зафиксировать здесь причину** (напр. «intrusive-list оказался непропорционально дорогим по
  времени, учебная цель по протоколу уже достигнута»). По умолчанию пишем сами.
- `capacity` конфигурируется; при `set` сверх лимита — вытеснение перед вставкой.
- **Критерий:** при `capacity=N` и N+1 ключах вытесняется именно наименее недавно
  использованный; `get`/`set`/`evict` — O(1) (подтвердить микробенчем/рассуждением).

### Этап 5 — Конкурентная модель + нагрузочный тест

- Финализировать thread-per-connection: аккуратное завершение соединения, обработка `write`-
  ошибок (клиент отвалился), отсутствие паник в хендлере.
- Проверить, что общий `Arc<Mutex<Store>>` корректен под параллельной нагрузкой (нет гонок —
  гарантируется системой типов + `Mutex`; проверить отсутствие дедлоков).
- **Нагрузочный тест настоящим инструментом:**
  `redis-benchmark -p 6379 -t set,get -n 100000 -c 50 -q`. Убедиться, что сервер держит
  многопоточную нагрузку без паник и деградации.
- Если мьютекс окажется узким местом — **не переусложнять сразу**; зафиксировать наблюдение,
  вынести шардирование/`RwLock` в POST_MVP.
- **Критерий:** `redis-benchmark` проходит без ошибок; понятны цифры throughput.

## Тестовая стратегия (сквозная)

Соответствует конвенции портфеля «тестам нужен интеграционный ярус»:

- **Юнит:** RESP-кодек (Этап 1) — включая фрагментацию; логика TTL и LRU в изоляции от сети.
- **Интеграция (детерминированный фейк, не только мок-HTTP):** поднять `Store` в памяти,
  прогнать реальные последовательности команд через настоящий кодек, без сети — детерминированно
  и быстро в CI.
- **End-to-end (ручной/по требованию):** настоящий `redis-cli` и `redis-benchmark` против
  запущенного бинаря — то, что мок никогда не поймает (реальная фрагментация TCP, поведение
  реального клиента).
