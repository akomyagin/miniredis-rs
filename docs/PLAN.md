# miniredis-rs — PLAN

## Видение

`miniredis` — учебный in-memory key/value сервер на Rust, который **сам реализует
проволочный протокол Redis (RESP)** поверх голого TCP. Это не HTTP-обёртка и не клиент к
настоящему Redis: сервер парсит бинарный протокол из потока байт, хранит данные в памяти,
поддерживает TTL и вытесняет ключи по алгоритму LRU за O(1).

Цель проекта — **искренняя техническая сложность и обучение**, а не продукт. Три темы, ради
которых он делается:

1. **Сетевые протоколы.** Корректный разбор RESP поверх *потокового* TCP: один `read()` может
   вернуть половину кадра, ровно один кадр или несколько кадров подряд. Наивный парсер
   «работает с `redis-cli` локально», но ломается при фрагментации пакетов в реальной сети.
2. **Структуры данных под конкурентный доступ.** Разделяемое KV-хранилище, к которому
   одновременно обращаются несколько соединений.
3. **Eviction-алгоритмы.** LRU с O(1) на `get` (touch) и на вытеснение — не просто `HashMap`
   с линейным поиском самого старого ключа.

## Архитектура (верхнеуровнево)

```
        TCP-соединения (redis-cli, redis-benchmark, любой RESP-клиент)
                              │
                    std::net::TcpListener
                              │  thread-per-connection
                    ┌─────────┴──────────┐
                    │  connection handler │   (по потоку на соединение)
                    │  ┌───────────────┐  │
   поток байт ─────▶│  │ resp::Parser  │  │  буферизующий, возобновляемый декодер:
                    │  │ (src/resp.rs) │  │  переживает фрагментацию TCP-чтений
                    │  └──────┬────────┘  │
                    │   команда (Array of Bulk)
                    │         ▼           │
                    │   dispatch: GET/SET/DEL/EXPIRE
                    │         ▼           │
                    └─────────┼───────────┘
                              ▼
                    Arc<Mutex<store::Store>>        общий для всех потоков
                    ┌──────────────────────┐
                    │ HashMap<key, Entry>   │  значение + expires_at + LRU-звенья
                    │ + intrusive LRU list  │  O(1) touch / evict
                    │ + capacity            │
                    └──────────┬───────────┘
                               │
                    background sweeper thread  ← периодически reap-ит истёкшие TTL
```

Два слоя, разнесённые по модулям:

- `src/resp.rs` — **протокольный слой**: кодек RESP, изолированный от логики хранилища.
  Именно здесь живёт вся сложность потокового парсинга.
- `src/store.rs` — **слой данных**: KV-хранилище, TTL, LRU. Ничего не знает о сети.

`src/main.rs` связывает их: слушает TCP, на каждое соединение запускает поток, гоняет парсер
над сокетом, диспатчит команды в хранилище, пишет RESP-ответы.

## Скоуп MVP

Только in-memory KV + TTL + eviction:

- RESP2-кодек (декодер + энкодер), устойчивый к фрагментации.
- Команды `GET`, `SET` (с опциями `EX`/`PX` для TTL), `DEL`, `EXPIRE`, плюс `PING` для
  проверки связи.
- TTL с ленивой экспирацией на доступе + фоновый sweeper истёкших ключей.
- LRU-вытеснение за O(1) при достижении лимита ёмкости.
- Конкурентный доступ: thread-per-connection, общее хранилище под синхронизацией.
- Нагрузочная проверка настоящими `redis-cli` / `redis-benchmark`.

## Этапы

| Этап | Содержание | Итог |
|---|---|---|
| 0 | Скелет: `cargo init`, модули-заглушки `resp`/`store`, `main` слушает TCP | `cargo check` чист |
| 1 | RESP-кодек: буферизующий возобновляемый декодер + энкодер | парсинг переживает фрагментацию |
| 2 | Команды GET/SET/DEL над `HashMap`+`Mutex`, диспатч, ответы | работает через `redis-cli` |
| 3 | TTL: `EXPIRE`/`SET EX`, ленивая экспирация + фоновый sweeper | ключи истекают |
| 4 | LRU-вытеснение O(1): intrusive linked list + HashMap (или крейт `lru`) | вытеснение при лимите |
| 5 | Конкурентная модель + нагрузочный тест `redis-benchmark` | стабильно под нагрузкой |

Детальная разбивка каждого Этапа — в [`TECHNICAL_PLAN.md`](TECHNICAL_PLAN.md).
